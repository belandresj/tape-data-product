# Dataset build and reproduction

The root [README](../README.md) is the full historical research report. The installed package provides a local path from reference/minute acquisition and screening through canonical trades/quotes, compact features, verified releases, causal queries, numerical analysis and figures. The offline demonstration uses invented inputs through those calculation paths. The imported historical report has **not** been regenerated by this package; exact historical inputs and full external acceptance remain separate requirements.

## Install and run the complete offline demonstration

From a clean checkout, with Python 3.13:

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install '.[dev]'
tape-product --help
tape-product demo --output output/demo
```

Use a new output directory on every run. The command generates two invented 720-second session-start prefixes, with 21,600 trades and 1,442 quotes. A fake paginated provider supplies reference membership, minute bars and events. The same screen used for vendor data selects the two symbols from a three-member reference universe; the third member remains in the denominator without minute bars. The calculator produces 1,440 feature/support rows, independently reconstructs them, builds and verifies a two-member release, executes the selected query, saves numerical report intermediates and renders seven synthetic figures.

The example begins at 04:00 ET, so initialization and 60s/300s maturity follow the production path. Its query closes at a censored prefix boundary. It is not a complete external symbol-day, independent market evidence or a reproduction of the report's GPUS/CAST comparison. Synthetic outputs live under the requested directory and never replace published report assets.

For live RSS observation, run from the source checkout:

```sh
python -B scripts/measure.py output/demo-resources.json tape-product demo --output output/measured-demo
```

Inspect `summary.json`, the `query` results, `analysis` numerical intermediates, `figures`, and each `stage.json`. Stage receipts bind effective inputs/settings, installed implementation/runtime identities and output files. Hash checks and independent numerical reconstruction answer different questions; neither validates trading expectancy.

## Individual stages

Commands accept explicit paths. Relative command paths resolve against the working directory; release member paths resolve against the containing manifest directory. JSON configuration paths follow the stage-specific rules in [acquisition](acquisition.md) and [report lineage](report-lineage.md). CLI `--help` is the authoritative argument reference.

### 1. Acquire reference membership and minute bars

```sh
tape-product acquire reference --config private/reference.json --output output/reference
tape-product acquire minutes --config private/minutes.json --output output/minutes
```

Supply explicit provider configuration and date/symbol selection. Credential values stay outside Git. The provider client uses bounded pages and retries, checks pagination destinations and requires terminal successful coverage before completion. For a larger universe, process symbol/date requests sequentially and concatenate the normalized minute JSONL records as a streaming preparation step. There is no implicit bulk acquisition.

### 2. Screen and acquire canonical pairs

```sh
tape-product screen --reference output/reference/reference.jsonl \
  --minutes output/minutes/minutes.jsonl --date 2026-06-18 \
  --minute-receipt output/minutes --output output/screen
tape-product acquire tq --config private/tq.json --output output/acquired
```

The T/Q configuration points explicitly to `output/screen/selection.jsonl`. The screen requires two consecutive eligible minutes, combined high/low log range ≥700 bps, at least 1,600 reported trades combined and at least 100 in each minute, within 04:00–20:00 ET. There is no dollar-volume screen. `denominators.json` retains reference members without usable bars. For a complete universe, provide one `--minute-receipt` per requested reference member, including successful empty responses, and concatenate minute files in that same order. Without those receipts the output explicitly records unverified minute-source coverage; it is not complete historical population evidence. Discovery is the first qualifying window's endpoint, not an invented vendor received-at timestamp.

Canonical pairs live under `tq/session_date=DATE/symbol=SYMBOL/`. Pair receipts bind SHA-256, bytes, rows, source and requested coverage. The acquisition stage creates the build inventory; it does not require an unexplained historical `selection.sqlite`. See [storage commands](acquisition.md) for verification, inventory assembly and explicit immutable R2 publication/staging.

### 3. Build features directly from the acquisition inventory

```sh
tape-product features build --inventory output/acquired/inventory.jsonl \
  --contexts private/contexts.jsonl --output output/features
tape-product features verify \
  --input output/features/session_date=2026-06-18/symbol=GPUS --reconstruction
```

This processes one member at a time and emits `output/features/partitions.jsonl` for release assembly. No conversion of selection or discovery JSON is needed. The inventory points to canonical pairs; production admission checks each exact selected record, symbol/date, endpoint and provenance against its pair receipt. Both source files and the receipt are rechecked after consumption, before completion.

The optional context JSONL contains records with `session_date`, `symbol`, `halts` and `continuity_breaks_ns` (UTC nanosecond timestamps). Missing records assert an empty overlay; they do not establish that historical halts or breaks were independently ruled out. Default calculation emits the full 57,600-second grid. **Do not execute this full external-data example until the measured resource checkpoint below is satisfied.** The demo uses explicit shorter, synthetic coverage.

For a single prepared pair, the alternative direct interface accepts `--quotes`, `--trades`, `--pair-manifest`, `--session-date`, `--symbol`, `--discovery`, `--halts` and `--continuity-breaks`. Its discovery JSON must be the exact screening selection record stored in the acquired pair. These direct flags cannot be mixed with `--inventory`; inspect `features build --help` for the full argument contract.

Each partition contains `features.parquet`, `support.parquet` and a completion manifest. All eighteen fields, masks and support rules follow the [feature contract](tape_data_product/README.md). `verify` checks integrity; `--reconstruction` additionally checks numerical reconstruction from stored support. The inventory build also saves a child-manifest ledger and stage receipt; missing children cannot silently shrink the expected release.

### 4. Reconcile a release

The acquisition and feature stages generate both inputs to release construction:

```sh
tape-product release build --expected-members output/screen/selection.jsonl \
  --partitions output/features/partitions.jsonl --output output/release
tape-product release verify --input output/release
```

Member paths in the generated partition index resolve against its containing directory. Duplicates, unexpected members, missing partitions, incompatible calculations and corrupted outputs fail completion. Expected members include symbols with zero subsequent query matches. The demo explicitly allows partial session-start members; its release remains labeled partial/synthetic. A new compatible release receives a new identity. Supply `--expected-release-hash` to `release verify` or `query` when exact replay identity is required.

### 5. Query and run the implemented pilot

```sh
tape-product query --release output/release \
  --config config/tape_cohort_300s_ms3_p050_selected_v1.json --output output/query
tape-product experiment threshold-pilot --release private/accepted-release --output output/pilot
```

Query output includes strict endpoint runs, causally activated intervals, per-window features, unavailable/available accounting, zero-match members and concentration. Every endpoint reaches the state machine. Five consecutive passes confirm entry at the fifth endpoint; economic exit confirmation does not backdate the exit. Halts, unavailable data and continuity breaks exit immediately. See the [query contract](query-contract.md).

The threshold pilot reproduces the fixed A–D participation comparisons and five development dates documented in [pilot results](../reports/pilot.md), using supplied accepted data. It does not tune thresholds. The separate estimator/persistence experiment awaits a stable source/test/configuration/result/renderer handoff and is not claimed as implemented here.

### 6. Aggregate and render the report

```sh
tape-product report aggregate --release output/release --screen output/screen \
  --tape-config private/tape-examples.json --output output/analysis
tape-product report render --aggregate output/analysis --output output/figures
tape-product report verify --input output/figures
```

Aggregation uses horizon-specific activity gates and per-panel eligibility, fixed histograms and bounded external ordering for exact ECDFs. Saved intermediates preserve zeros, ties, off-axis mass, denominators and concentration. Rendering reads only those intermediates and can be repeated without T/Q acquisition or a remote scan.

The [report lineage table](report-lineage.md) identifies each of the seven published figures and headline tables, required historical inputs, exact example intervals, code paths and verification status. Missing historical numerical inputs remain missing; no values are inferred from figure pixels.

## Skip stages when verified inputs already exist

Accepted canonical T/Q pairs plus discovery and overlay context allow starting at feature calculation. Accepted feature partitions allow starting at release reconciliation. A compatible verified local release allows query and analysis. Saved verified numerical intermediates allow rendering alone. Reuse always preserves the original identities and checks declared completeness; a smaller available subset is not a complete historical release.

## Resource checkpoint and evidence

The [architecture](architecture.md) states time/memory/disk bounds. Inputs are projected in batches ≤25,000 rows (4,096 default), histories are bounded and exact distribution sorting spills to disk. Ordinary synthetic checks run sequentially under a 768 MiB process-tree stop with 50 ms sampling. See [verification](verification/README.md) for actual measurements and tested environments.

Before any full external symbol-day, week, corpus or external-drive acceptance: inspect allocations; measure the exact final production path on a representative session-start prefix/member set; record input rows, elapsed time, peak worker-plus-descendant RSS, transferred bytes and spill/output disk; project full-run costs; then obtain confirmation. A random mid-session slice does not supply mature rolling state. No full historical run, bulk acquisition, upload/delete or publication is part of offline acceptance.
